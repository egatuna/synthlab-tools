  For a solo studio that prospects maybe 30 companies a month, paying $79 for a seat in a tool built for a 10-person sales team never made sense. We kept paying because switching felt like work.

## 2026-07-02 (Thu)
### X
- [ ] Stack for synthlab-tools: Python, YAML configs, markdown output. No databases, no dashboards, no Docker. Every tool is a script you can read in 10 minutes and modify in 5. That constraint was a choice, not a limitation.
### LinkedIn
- [ ] Day 4 of the synthlab-tools series. Today: the architecture.
  
  I made a deliberate decision early: every tool in this suite has to be readable by someone who didn't write it. That ruled out frameworks, ORMs, background job queues, and web UIs.
  
  Each tool is:
  — A Python script
  — A YAML config file
  — Markdown or CSV output
  
  No database. If a tool needs to persist state between runs, it writes a file. If it needs configuration, it reads YAML. If it produces output, it writes markdown.
  
  This sounds like a step backward from a proper application. It is. It's also the right call for tooling a single operator uses 10 times a week. The overhead of a database and a web interface adds weeks of build time and a permanent maintenance surface. Neither pays off for internal tooling at this scale.
  
  The tradeoff: no dashboards, no history views, no user management. You also get a tool you can fully understand in one sitting and modify without breaking anything downstream.
  
  When I need to change how contact-hunter formats its output, I edit one file. No migrations, no API version bumps, no frontend changes. That's the return on the simplicity constraint.
  
  Next in the suite: a client onboarding automator and a project status tracker. Same pattern, different jobs.

### LinkedIn
- [ ] Day 6 of the synthlab-tools series. What I got wrong.
  
  I started building a reporting dashboard for seo-scout. Spent four hours on it. Then I asked myself when I would actually open a browser to look at a chart instead of reading the markdown file the script already outputs.
  
  The answer was never. I killed the dashboard.
  
  I started building a sync feature for contact-hunter to push contacts directly to a Google Sheet. Spent three hours on the OAuth flow. Then I realized we export the CSV and paste it manually maybe once a week. Three hours to save 45 seconds.
  
  I killed the sync.
  
  These weren't wasted hours. They were the hours that clarified what these tools actually need to do. The pattern every time: I built something because it seemed useful in the abstract. I cut it when I couldn't describe a specific workflow where it would get used.
  
  The question that saved the most time: "Describe the last three times you would have used this feature."
  
  If you can answer that concretely, build it. If you find yourself saying "well, in cases where..." or "it would be nice when..." — don't build it.
  
  The tools that shipped are lean because I held that standard. The graveyard of cut features is part of the work, not a failure of it.
